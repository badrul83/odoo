# PHP ERP Foundation

This is the isolated PHP/MySQL migration target. The existing browser application remains untouched while the server-backed ERP is built and its data migration is reconciled.

**Deployment security:** For any internet-facing deployment, set the web document root to `php-erp/public`. The legacy workspace root (`index.html` and `app.js`) is a browser-only prototype with no server-side sign-in and stores ERP records in `localStorage`; do not publish that root for real business data. The `php-erp/.htaccess` rules add defense in depth when the migration folder is below `htdocs`, but they do not authenticate or hide the legacy root application.

## Local setup

1. Create an empty **MySQL** database and a dedicated database user. The PDO `mysql:` driver is the PHP client interface; it does not mean a MySQL server is already connected. This workspace contains only `.env.example`, so set the environment values for the target MySQL server before running migrations. Disposable QA results produced with MariaDB are compatibility checks only, not evidence that this application is connected to or deployed on MariaDB.
2. Set the `ERP_DB_*`, `APP_BASE_URL`, `APP_TIMEZONE`, `ERP_STORAGE_PATH`, and `ERP_DATA_ENCRYPTION_KEY` values from `.env.example` in the PHP/Apache environment. `APP_BASE_URL` must be the final public origin and path (for example, `https://example.com/erp`) when installed in a subfolder; the UI, APIs, logos, and public booking links use that base path. Store uploads and sessions outside the public document root. Company and branch logos are private files in `ERP_STORAGE_PATH/company-logos`; the authenticated API streams validated PNG/JPEG/WebP images. The PHP `openssl` extension is preferred for AES-256-GCM bank-data and authenticator-secret encryption; `sodium` secretbox is supported as a fallback. Session files default to the private `storage/sessions` directory; set `ERP_SESSION_PATH` if the cPanel account requires a different writable path. Generate a 32-byte encryption key (for example, `openssl rand -base64 32`), store it outside the web root, and back it up securely; changing it without re-encrypting stored bank and authenticator data makes those details unreadable. Recovery codes are the 2FA fallback if the key is lost. Never use the XAMPP `root` account or an empty password for a hosted deployment.
3. For the included `APP_BASE_URL=http://localhost` example, point the local virtual host/document root at `php-erp/public` and enable Apache `mod_rewrite`. If serving from the XAMPP `htdocs` project path instead, set `APP_BASE_URL` to that public path (for example, `http://localhost/ODOO/php-erp/public`). Keep `app`, `bin`, `database`, and all secrets outside the public document root.
4. Run the schema migrations from the project root with the same environment variables:

   ```powershell
   $env:ERP_DB_HOST = '127.0.0.1'
   $env:ERP_DB_PORT = '3306'
   $env:ERP_DB_NAME = 'erp_database'
   $env:ERP_DB_USER = 'erp_user'
   $env:ERP_DB_PASSWORD = '...'
   & 'C:\xampp\php\php.exe' .\php-erp\bin\migrate.php
   ```

   Migration `052_products_create_permission.sql` adds the standalone Products → Create user right. It is not applied until a project MySQL connection is configured and the migration runner is executed.
   Migration `053_contact_master_data_create_permission.sql` adds the separate Contact → Creation right and backfills it for existing roles with Contacts write access. Contact creation is available without exposing the Contacts directory; browse and update permissions remain separate. This migration also needs the configured MySQL connection and migration runner.
   Migration `054_master_data_export_permission.sql` adds `Export → Allowed`. The Contacts and Products CSV exports require the corresponding read permission and enforce company scope server-side. Contact bank/UBO and accounting fields remain governed by their individual read rights. Exports are only implemented for Contacts and Products so far. This migration also needs the configured database connection and migration runner.
   Migration `063_product_class_carton_pricing.sql` adds the Product Class (CP / Non-CP / Unclassified), Carton Size, Units per Carton, and Carton Price fields used by Product configuration and the Products CSV import/export. Piece Price is the default Sales Price per selected Sales Unit; when it is blank, import derives it from Carton Price and Units per Carton when both are available. Apply migration 063 before using the added fields. The product import accepts Excel UTF-8 CSV files up to 5 MB and 2,000 rows, and saves the whole file atomically. This migration is not applied here because no project database is configured.
   Migrations `055_partner_commission_permissions.sql` and `056_partner_commission_plan_management.sql` add company-scoped Partner Commissions read, assignment, and management rights; existing Contacts writers retain read/assignment but do not gain plan management. Sales includes a Commission Plans list and atomic create/edit/archive dialog with all screenshot plan and rule fields. Active saved plans are available to the Contact assignment field. Migration `057_sales_quotation_templates.sql` adds company-scoped quotation template terms, validity, pricelist, product lines, and the quotation-to-template reference. Templates can be created, edited, archived, applied to quotations, and used by Commission Plan rules. Odoo 20 template features still pending are recorded in `../ERP20_PHP_IMPLEMENTATION.md`, along with Sales commission accrual/settlement and the broader ERP checklist. Apply migrations with the configured database connection and migration runner; this project currently has no database connection configured.

   Inventory → Cycle Counts requires migration `042_inventory_cycle_counts.sql`. It adds location frequency dates and company-scoped count headers/positions with stock-move and optional Perpetual accounting links. This migration has not been applied in the current workspace because no project database is configured.

   Inventory → Warehouses provides company-scoped Warehouse and Location create/edit/archive/restore flows using the existing `warehouses` and `stock_locations` schema; no additional migration is required. Creating a warehouse generates its standard Stock/Input/Output locations and any missing company-level virtual locations; Sales, Purchase, Inventory, Cycle Counts, Manufacturing and valuation use the shared records. Warehouse code edits refresh the root and descendant paths. Custom Internal/View locations support same-warehouse parent hierarchy, barcode, inventory frequency and derived count dates; virtual locations and warehouse roots are system-managed. Archive guards check active children, stock/reservations, pending moves, active counts and active Manufacturing Orders. Contact linking requires company-scoped Contact read access. Static PHP/JavaScript checks pass, but there is no project database connection for persistence or browser integration verification.

   User Profile → Preferences includes a default warehouse scoped to the selected default company. Migration `061_user_default_warehouse.sql` adds the foreign-key-backed user preference. Active warehouse choices are loaded from the Inventory warehouse master; the server rechecks company access and warehouse ownership before saving. The authenticated session exposes the preference and new Sales/Purchase orders select it when it belongs to the order company, falling back to the first active warehouse otherwise. An unchanged archived warehouse remains visible as unavailable so saving other profile preferences does not silently clear it. Apply migration 061 before using this preference; database persistence and browser interaction remain unverified because this project has no configured MySQL connection.

   Inventory → Categories & Units lists product categories, UoM categories, and units/conversions, and supports company-scoped create, edit, archive, and restore using the existing migration `006_inventory_master_data.sql` tables. Shared/global masters remain read-only. Parent/category scope, conversion factors, rounding, and the one-active-Reference-unit rule are validated before save. Product category costing/valuation and used UoM conversion values are protected from unsafe changes. New category/UoM records are available to the existing Product, Stock Move, Sales/Purchase, and Manufacturing selectors. This flow has not been exercised against the unconfigured application database.

   Customer Invoicing → Credit Notes and Refunds / Applications requires migrations `043_customer_credit_notes.sql`, `044_customer_credit_note_refunds.sql`, and `050_customer_credit_note_applications.sql`. Migration 044 adds company-scoped refund payment, receivable allocation, refund sequence, and bank-match records. Registering a refund from a posted credit note posts the customer receivable and Outstanding Payments entry; matching the exact negative bank line clears Outstanding Payments to Bank/Cash. Migration 050 adds partial/full application of posted customer credits to another open invoice for the same company, customer, and company currency, linked through the existing posted Receivable items. Refunds remain separate from invoice applications. These migrations have not been applied because no project database connection is configured.

   Inventory → Customer Returns and Purchase → Supplier Returns require migration `045_customer_stock_returns.sql`, which adds shared return move/line links. Customer returns link to validated Sales delivery lines, cap quantity against prior returns/reservations, restore original delivery valuation, and reduce delivered-quantity invoicing. Supplier returns start from a validated Purchase receipt, return Goods to its original Vendor location, preserve lot/serial lineage, cap unreturned quantities, update physical stock valuation, and reduce received-quantity / three-way-match totals. Physical supplier returns do not automatically create a supplier credit note; create a separate financial credit note. Customer Credit Notes → Customer Returns and Perpetual COGS reversal require migration `046_credit_note_customer_return_cogs.sql`. It snapshots the invoice's delivery valuation-layer allocation, reserves completed return quantities against those source layers, links exact return moves to credit-note lines, and posts a balanced Stock Valuation / COGS reversal with the credit note. Physical returned quantity is separate from financial credit quantity; price-only credits leave it at zero. Migrations `043`–`050` have not been applied in the current workspace because no project database connection is configured. Historical Perpetual invoices without the new cost-layer snapshot cannot be auto-linked for COGS reversal and need a reviewed backfill before enabling return allocations for those invoices.

   Purchase → Supplier Credit Notes requires migrations `047_vendor_credit_notes.sql`, `048_vendor_credit_note_refunds.sql`, and `049_vendor_credit_applications.sql`. A posted Vendor Bill can create one full-amount draft credit note; posting swaps every line of the original posted bill entry to make an exact balanced reversal. Users can register partial cash refunds up to the open credit balance and manually match or import-match an exact positive bank line. They can also apply a partial or full credit to another posted bill for the same company, supplier contact, and company currency; the application links the credit-note debit and bill payable lines and updates both residuals without creating a cash entry. The bill search supports bill-number/reference lookup beyond the latest 100 rows. Supplier Contacts show posted credit, refund-registered, credit-applied, and open-credit totals; each affected bill shows the credit application links. Migration 048 adds refund sequences, postings, allocations, statement links, and backfills existing posted notes with their open credit balance; 049 adds applied-credit balances and payable-line allocation links. Physical supplier returns are handled separately in Inventory and do not auto-generate credit notes. Partial credit-note quantities remain future work. Migrations 047–049 are not applied here because there is no project database connection.

5. Create the first administrator from the terminal. Set `ERP_BOOTSTRAP_COMPANY_NAME`, `ERP_BOOTSTRAP_ADMIN_NAME`, and `ERP_BOOTSTRAP_ADMIN_LOGIN`; the command generates and prints a one-time password, refuses to run once any user exists, and does not write the password to a file:

   ```powershell
   $env:ERP_BOOTSTRAP_COMPANY_NAME = 'Your Company'
   $env:ERP_BOOTSTRAP_ADMIN_NAME = 'Administrator'
   $env:ERP_BOOTSTRAP_ADMIN_LOGIN = 'admin@example.com'
   & 'C:\xampp\php\php.exe' .\php-erp\bin\create-first-admin.php
   ```

   If a company already exists, also set `ERP_BOOTSTRAP_COMPANY_ID` to its ID. Store the generated password securely and rotate it after sign-in.

6. Open `/health`. It reports only whether the database connection works; it does not expose connection details. Obtain a CSRF token from `/api/v1/auth/session` before calling the login/logout API.

## User security and API keys

The signed-in user can enroll authenticator-based 2FA from their profile's Security tab. This requires `ERP_DATA_ENCRYPTION_KEY` and PHP OpenSSL or Sodium. Apply migration 038 first. Save the recovery codes when enrollment completes; each is displayed once. API keys are created from the same Security tab after current-password confirmation, expire in 30, 90, or 365 days, inherit the user's permissions and allowed companies, and are displayed only once. Send the token over HTTPS as `Authorization: Bearer erp_<token>`; revoke keys from the dialog. Do not put API keys in browser code, source control, public URLs, or logs.

User Profile → Security also supports passkeys. Apply migration `062_user_passkeys.sql` first. Add or remove a passkey only after confirming the current password. Passkey sign-in requires a browser with WebAuthn support and a secure origin (HTTPS; localhost is allowed), and honors the existing 2FA challenge. Configure `WEBAUTHN_RP_ID` and the exact `WEBAUTHN_ORIGIN` in the private environment file before hosting; the `.env.example` values are for localhost only. The current implementation accepts ES256 P-256 credentials with `fmt=none` attestation.

User Profile → Calendar saves each user's default Day/Week/Month/Year view and weekend visibility. Migration 039 adds these fields; apply it with the normal migration runner before using this preference panel.

Accounting → Bank Statements imports UTF-8 CSV files up to 5 MB and 5,000 rows. Required columns: `Date` (`YYYY-MM-DD`) and signed `Amount`. Optional columns: `Reference`, `Description`, `Currency`, `Partner Email`, and `External ID`. Comma, semicolon, and tab delimiters are supported. Enter the opening and closing balances; the import checks that opening balance plus signed transaction amounts equals closing balance in the selected company's currency. Exact matching covers an unreconciled customer receipt or supplier refund on positive lines, and a vendor payment or customer credit-note refund on negative lines, in the same company, Bank/Cash journal, currency, and amount. Other statement items can use the existing one-line account categorization workflow. Migration 040 adds the storage and match links; apply migrations to the configured **MySQL** database before using this feature. This workspace currently has no configured application database connection.

Example authenticated API request:

```sh
curl -H 'Authorization: Bearer erp_REPLACE_WITH_YOUR_KEY' \
  'https://example.com/erp/api/v1/auth/session'
```

## To-do deadline reminder cron

To-do reminders appear in the signed-in user's Notifications inbox. The scheduled worker runs from CLI, checks the due date against each company's time zone, notifies assigned users (or the task creator when there are no assignees), and safely ignores duplicate runs. Configure cPanel Cron Jobs to run it every five minutes, using the same private `ERP_DB_*` environment values as the website:

```sh
*/5 * * * * /usr/local/bin/php /home/ACCOUNT/private/erp/php-erp/bin/process-todo-reminders.php >> /home/ACCOUNT/logs/erp-reminders.log 2>&1
```

Replace the PHP binary, account paths, and log path with the values for the hosting account. Keep the `php-erp` application files and logs outside `public_html`, and configure the cron environment without placing database secrets in a public file. Apply migrations before enabling the job. Reminder delivery is in-app; it does not send email or WhatsApp.

Do not deploy the current browser prototype or its snapshot backup endpoint as the production ERP backend. The platform foundation is not yet a finished or production-ready ERP; see [`../ERP20_PHP_IMPLEMENTATION.md`](../ERP20_PHP_IMPLEMENTATION.md) for scope, known gaps, and completion gates.
