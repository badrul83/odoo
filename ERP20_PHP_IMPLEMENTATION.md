- Sales quotation editing now detects a stale form after acquiring the order lock by comparing the persisted document-and-line fingerprint with the form's original snapshot. It also rereads the latest approval state before replacing lines. Sales confirmation reloads the full order and lines while holding the parent row lock, then computes the approval fingerprint and delivery moves from that locked snapshot. ## Required end-to-end flows

### Lead to cash

Contact/lead → opportunity and scheduled activities → quotation and approval → sales order → stock reservation/picking → delivery validation → customer invoice/credit note → payment → bank/cash reconciliation → balanced ledger and customer statement.

### Request to pay

Supplier Contact → RFQ → approval → purchase order → receipt/quality/lot capture → vendor bill or bill-to-receive accrual → payment → bank reconciliation → balanced ledger and supplier statement.

### Inventory and stock valuation

Product and unit setup → DEPO warehouse/location setup → purchase receipts, reservations, sales deliveries, internal transfers and stock adjustments → cost valuation → accounting entries and Dashboard balances.

### Company and access administration

Company/branch setup → users and linked Contacts/employees → allowed companies/default company → role and per-app groups → approval layers → record visibility and allowed actions → audit log. Every server request must enforce these permissions; hiding a UI control is not authorization.

## Shared data rules

- A Contact is the canonical partner record. Customer, supplier, employee, salesperson, buyer, and other roles refer to its stable database ID; never join business records by display name alone.
- Every transactional document has a company/branch, owner, sequence/reference, dates, currency, state, source links, and immutable audit events.
- Document lines reference canonical products, units, taxes, accounts, and analytic dimensions. Quantities and currency amounts use decimal database types, not binary floating point.
- Confirmed, posted, paid, delivered, received, cancelled, and reversed are distinct states with explicit allowed transitions and authorization checks.
- Posting creates balanced journal items. Stock moves and inventory valuation reconcile to the corresponding accounting entries according to the selected policy.
- Use soft archival where business history must remain auditable. Deletion of posted/linked transactions is not allowed; reverse them instead.
- Multi-company rules apply to every read, write, search, export, report, and linked-record action.

### Bank statement CSV import, payment matching, and account categorization milestone — 2026-11-20

Migration `040_bank_statement_import.sql` adds company/journal-scoped statement headers and transaction lines, idempotency by original file SHA-256, and nullable unique links from imported lines to the existing customer/vendor payment match ledgers. The Accounting view accepts UTF-8 CSV (comma, semicolon, or tab delimited; 5 MB/5,000-row limits). Required columns are `Date` (`YYYY-MM-DD`) and signed `Amount`; optional columns are `Reference`, `Description`, `Currency`, `Partner Email`, and `External ID`. Import validates active Bank/Cash journal, selected company access, company currency, nonzero exact decimal amounts, opening + signed transactions = closing, and duplicate file/transaction constraints.

Each unmatched row can search unreconciled posted customer receipts (positive statement amount), vendor payments (negative amount), or registered customer credit-note refunds (negative amount) with the exact company, journal, currency, and amount. Selecting a candidate uses the existing payment reconciliation transaction: it checks the fiscal lock date, posts the bank/outstanding clearing entry, updates invoice/bill payment status, records audit data, and ties the source statement line to the match. When there is no payment candidate, a user with both Accounting Reconciliation and Posting access can select an active same-company counterpart account and post one balanced entry: positive lines debit Bank/Cash and credit the selected account; negative lines debit the selected account and credit Bank/Cash. Receivable, payable, cash, and off-balance accounts are excluded from this categorization picker. This covers direct fees, interest, and transfers posted to a clearing/other account; it does not pair a transfer's two bank lines, calculate tax, or create automatic write-offs. The posting uses the statement transaction date, obeys the accounting lock date, and creates an audit event. A statement becomes reconciled only after every imported line has a customer-payment, customer-refund, vendor-payment, or account-categorization link. Partial/grouped matching, opening balances as lines, and foreign currency remain unsupported; lines are never auto-posted.

### Customer stock returns from validated deliveries — implementation pending database setup

Migration `045_customer_stock_returns.sql` adds parent delivery and reason links on stock moves plus original delivery line links on move lines. The Inventory detail for a completed Sales delivery to a customer exposes `Return Products` when some delivered quantity remains returnable. ### Customer return ↔ credit note ↔ COGS integration — implementation pending database setup (2026-11-21)

Migration `046_credit_note_customer_return_cogs.sql` adds a per-invoice-line snapshot of the exact delivery valuation layers used when posting Perpetual COGS, and a company-scoped allocation from credit-note lines to completed Inventory return move lines. A credit note remains a financial reversal. Its form also asks how much of each credited Goods quantity has physically returned; only a validated Inventory return may be selected. The server matches returned quantity to the same Sales Order line and, for Perpetual invoices, the same outbound valuation layer, reserving quantities against active draft/posted credit notes. It consumes return lines in delivery/return order and preserves lot/serial references. The credit-note detail displays the returned quantity and links each source Stock Return into Inventory. Discarding a draft credit note releases its return allocations because only active drafts and posted notes reserve stock.

When a linked credit note is posted, the Accounting entry still reverses Receivable, Revenue and Tax. It also debits the original Stock Valuation account and credits the original Cost of Goods account for the returned quantity's share of the source invoice's saved cost allocation. Money rounding is distributed cumulatively per valuation layer and cannot reverse more than the source COGS. The entire move must balance before posting. A credit for a price adjustment with no physical return leaves Return Quantity at zero and creates no stock/COGS lines. Periodic valuation can link a physical return to the credit note but does not create a COGS reversal, because the source invoice has no Perpetual COGS entry. Inventory valuation remains governed by the Inventory return move.

### Sales quotation template flow — 2026-11-21

Quotation templates are company-scoped and can be managed from Sales. Each template stores its name, optional pricelist, terms and conditions, expiration days (0 means indefinite), and 1–200 validated product lines. Each line stores product, description, quantity, unit, unit price, discount, and tax. Applying a template replaces the current line set and terms after confirmation when the user has already entered products; it also applies the configured pricelist and computes expiration from the quotation date. Saving the quotation preserves its template reference. Templates can also be chosen as Commission Plan rule criteria. The API validates company access, product and UoM compatibility, pricelist and tax availability, CSRF, and records template changes in the audit log.
